# ADC Nexus 软件设计规格（SDS）

版本：JDBC 1.0.0-rc1 发布候选规格，2026-10-21。SDS 在这里指 Software Design Specification：可执行实现的规格，不是特定编程语言。

## 权威来源与实施原则

业务来源为《安德鲁牙科连锁运营管理系统分析与设计报告》状态图与文辞精修版（83 页，SHA256 `91dd39b6ab96843f0023fe97f50245c3e991eff4ccca427f5861ac91eb4c4a60`）。原文全部 18 项用例、四张状态图、六张内部序列图和 61 表模型是本实施的核对基线。原有 TypeScript/D1 程序作为设计资产与行为参考保留。本目录独立实现 Java JDBC 数据访问，不依赖 JPA/Hibernate。

实现状态必须由测试证据认定；本文不将目标写成已发布事实。外部短信/微信缺少机构凭据时返回明确的不可用状态。收退款登记经人工核实的凭据，不执行支付划转。系统提供课程合成数据环境，不能将课程验证描述成真实医疗机构上线。

## 架构

浏览器 → 同源 HTTPS → Java 21 HTTP 控制器 → 授权与应用服务 → JDBC PreparedStatement/事务 → PostgreSQL。开发时同一服务可使用 SQLite JDBC。静态资源随 Java 包部署，不需要独立 Node 运行时。Java 层承担全部权限、状态、金额与时段校验。公开环境禁止将 SQLite 文件放到临时文件系统。

预定低成本部署为 Render 免费 Java 容器 + Neon 免费 PostgreSQL。免费套餐可能休眠，启动等待不是业务失败；不承诺付费级可用性。正式部署、数据库恢复和实际外部身份通道分别验收。

## 状态与业务规则

预约：CONFIRMED → CHECKED_IN → IN_PROGRESS → COMPLETED；CONFIRMED → CANCELLED / NO_SHOW。撤销到诊仅在无实施治疗、无签署记录时允许并保留取消/更正原因。NO_SHOW 仅在服务结束并超过配置宽限后成立。取消必须有发起方和原因。

就诊：SAFETY_REVIEW / WAITING → IN_PROGRESS → COMPLETED。风险复核不代替项目资格，同意记录不代替病历签署。实际治疗、方案和收费行有各自身份。

结算：ISSUED、PARTIALLY_PAID、PAID、VOID。净收款为有效收款减有效退款；退款后按净收款重算，不视 PAID 为不可逆终态。计划不进入应收，历史价格不随目录修改。

季度：OPEN → CLOSED；重开要独立权限和理由。净利润 = 核定收入 − 治疗成本 − 运营费用；基金 = max(全网季度净利润,0) ×10%。个人贡献可以由已批准分摊计算，个人奖金分配制度未获确认，不编造个人奖金公式。

## 持久化与并发

保留基线 61 张表、730 个字段与 119 条已声明外键。实施增补逐项目同意、牙医费用归属、病史版本、不可变版本签署四张业务证据表，以及迁移版本与幂等收据两张技术表；合计 67 张表、130 条外键。原报告的 61 表图版仍作为设计基线，实施后的完整图版与数据字典须随最终报告更新，不能混淆两组统计。PostgreSQL 将原 INTEGER 映射为 BIGINT（包括原数值布尔标记，仍遵守 0/1 语义），TEXT 保留本地 ISO 时间；金额使用整数分。外键在全部建表后创建。SQLite 测试版使用同一逻辑结构。

所有外部输入绑定参数。版本控制的初始化 DDL 和合成种子脚本通过 Statement 批处理，不接受外部拼接输入；业务访问使用 PreparedStatement。PostgreSQL 配置 HikariCP 连接池，最多 8 条连接，空闲连接可回收，不主动维持云数据库常醒。事务写入取得固定业务互斥锁：PostgreSQL 使用事务 advisory lock，SQLite 使用 IMMEDIATE 写事务。互斥覆盖资源、资金与期间核定，避免进程内锁在多实例失效。读取不占该锁。关键对象仍用乐观版本检查；失败整笔回滚。生产扩容前可按资源粒度细化锁并做负载试验。

## 权限和安全

角色：前台、牙医、收费员、诊所经理、总部运营、总部财务、权限管理员、患者。角色权限由表中关系定义；诊所范围及生效日期在每次请求校验。牙医临床修改还须对应负责牙医。患者入口以核实绑定而非客户端 ID 判断。错误不回传 SQL、密码或无权记录内容。

登录界面提供员工、医师、患者入口，并可选员工岗位。选择入口不会授予权限；密码校验后须核对数据库中已授予的有效角色，入口不匹配时拒绝登录。医师默认进入自己的临床队列，患者默认进入本人空间，前台进入日程，收费员进入收费台，经理进入本店运营，总部财务进入季度核定，管理员进入授权管理。导航由服务端返回的权限生成，页面直接访问与 API 再次验证相同权限。读权限不自动包含写权限，跨店汇总不自动开放病历明细。

会话采用 HttpOnly、SameSite cookie；TLS 部署启用 Secure。变更接口检查同源与 CSRF。敏感响应禁缓存。静态资源设置 CSP。课程公开演示入口仅在显式 DEMO_MODE 下启用，使用合成数据和真实数据库写入，明确其演示身份；正式业务关闭该入口。

## 验收与交付顺序

1. 可执行 schema 与报告基线逐表比对；2. 角色/范围拒绝测试；3. 预约到诊—治疗计划/同意—实施签署—完成—结算—收退款全流程；4. 候补、排班变更与并发；5. 费用分摊与期间关闭/重开；6. 手机与宽屏界面；7. PostgreSQL 实测、云部署及备份恢复；8. 根据实际证据更新报告、图表、目录和可追踪矩阵。

未完成第 7 步不得将本地地址称为正式发布链接。原报告在验收前保留完整原件。

## 当前验收边界

本地 SQLite JDBC、独立 PostgreSQL JDBC 和打包 JAR 均通过业务集成验收；最新条目、数量及数据库恢复证据见 `qa/` 实际 JSON。测试固定业务日期以覆盖到期季度关闭，不冒充真实发生的诊疗。公开云端链接、托管重启持久化和云端恢复尚未验收。短信/微信找回、临床文件新增上传、支付划转、逐次服务端导出审计、第三方法律签章以及机构经营核算制度均不能标记为已完成。

组合岗位按“具体权限对应的有效授权范围”计算，不以角色范围简单并集扩大其他权限。收费员的患者身份查询不返回过敏、病史、联系人或临床时间线；医师临床明细与修改限本人负责就诊。季度结束前只允许预览，不能正式关闭。

发布前加固：写事务中重新核验会话和当前操作范围，成功幂等收据不豁免后续授权变化；账户治理为总部级管理员职责，不能授予单店管理员角色来扩张权限。JSON 只接受对象，拒绝重复键、尾随对象、超限及错误媒体类型。业务请求遇到连接中断只自动重试一次，沿用原幂等标识；登录不自动重放。排班更新在事务内检查更新后的完整有效规则集，改变星期、起止日期或时段均不得使既有有效预约失去覆盖；失败整笔回滚。
